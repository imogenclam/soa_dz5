# Аналитика онлайн-кинотеатра

Когда зритель включает фильм, Movie Service публикует событие в Kafka. ClickHouse сохраняет его вместе с другими действиями зрителей. По этим данным сервис аналитики на Python рассчитывает показатели за день. В Grafana видно, какие фильмы смотрят чаще и какая доля зрителей возвращается. Для ежедневной выгрузки в S3 сервис берёт готовые метрики из PostgreSQL.

## Запуск

```powershell
docker compose up -d
```

При запуске Compose создаёт топик `movie-events` и регистрирует схему Avro. Миграции обеих баз выполняются автоматически. Когда таблицы ClickHouse готовы, генератор добавляет события за предыдущие 14 полных дней.

| Сервис | Назначение | Переменная порта |
| --- | --- | --- |
| [Grafana](http://localhost:3000/d/cinema-analytics) | Дашборд с дневными метриками без авторизации | `GRAFANA_PORT` |
| [Movie Service](http://localhost:8000/docs) | Приём событий по HTTP | `PRODUCER_PORT` |
| [Aggregation Service](http://localhost:8001/docs) | Пересчёт метрик и экспорт за выбранный день | `ANALYTICS_PORT` |

Порты сервисов доступны только на `localhost`. Метрики появляются в Grafana после первого расчёта. Команда `docker compose logs -f analytics` показывает ход расчёта. Пауза между циклами по умолчанию составляет 60 секунд и задаётся переменной `AGGREGATION_INTERVAL_SECONDS`.

В выводе `docker compose ps -a` разовые задачи имеют статус `Exited (0)`, когда их работа успешно завершена. Это относится как к миграциям `ch-migrate` и `pg-migrate`, так и к подготовке Kafka (`bootstrap`) и загрузке примеров (`seed`).

## Автоматическая проверка

```powershell
docker compose --profile test run --rm tests
```

Интеграционный тест отправляет события по HTTP, а затем сверяет каждое поле с записью в ClickHouse. В тестовый день трое зрителей начали просмотр, а четвёртый только искал фильм. Поиск тоже учитывается в DAU, поэтому за день активны четыре пользователя. Двое из трёх досмотрели фильм, так что конверсия равна 2/3. При длительности завершённых просмотров 60 и 120 секунд среднее составляет 90 секунд.

Тест повторно отправляет одно завершение с тем же `event_id` и проверяет, что конверсия по-прежнему равна 2/3. Отдельные проверки сравнивают архив в S3 с данными PostgreSQL и выполняют запросы панелей Grafana.

## Пример обработки события

Зритель `viewer-42` включает фильм `arrival` на телевизоре. Данные события (`$event`) и дата расчёта (`$day`) сохраняются между шагами в одном сеансе PowerShell.

### Публикация события

```powershell
$stamp = [datetime]::UtcNow
$day = $stamp.ToString('yyyy-MM-dd')
$event = @{
    event_id = [guid]::NewGuid().ToString()
    user_id = 'viewer-42'
    movie_id = 'arrival'
    event_type = 'VIEW_STARTED'
    timestamp = $stamp.ToString('o')
    device_type = 'TV'
    session_id = [guid]::NewGuid().ToString()
    progress_seconds = 0
}
Invoke-RestMethod http://localhost:8000/events -Method Post -ContentType 'application/json' -Body ($event | ConvertTo-Json)
```

После подтверждения от Kafka сервис возвращает HTTP 201 и `event_id` принятого события.

### Поиск события в ClickHouse

```powershell
$id = $event.event_id
docker compose exec -T clickhouse clickhouse-client -u cinema --password cinema_local -q "SELECT event_id, user_id, movie_id, event_type, progress_seconds FROM cinema.events FINAL WHERE event_id = '$id'"
```

ClickHouse читает события пачками, поэтому первый `SELECT` может вернуть пустой результат. После записи пачки тот же запрос вернёт строку `VIEW_STARTED` для зрителя `viewer-42`.

### Пересчёт метрик за день

```powershell
Invoke-RestMethod "http://localhost:8001/recalculate/$day" -Method Post
docker compose exec -T postgres psql -U cinema -d cinema -c "SELECT metric, dimension, value FROM daily_metrics WHERE day = '$day' ORDER BY metric, dimension"
```

В PostgreSQL у строки `movie_views` для фильма `arrival` поле `value` содержит число начатых просмотров за день.

### Экспорт в S3

```powershell
Invoke-RestMethod "http://localhost:8001/export/$day" -Method Post
"fs.cat /buckets/movie-analytics/daily/$day/aggregates.json" | docker compose exec -T s3 weed shell
```

Поле `computed_at` в JSON содержит время расчёта. При повторном экспорте за ту же дату сервис обновляет файл под прежним ключом.

## Как устроена система

```text
Movie Service → Kafka (movie-events) → ClickHouse (события)
                                              ↓
                                      Aggregation Service
                                        ↙            ↘
                         ClickHouse (метрики)       PostgreSQL
                                  ↓                     ↓
                               Grafana              экспорт в S3
```

### Доставка событий

Ключом сообщения служит `user_id`, поэтому события одного зрителя попадают в одну из трёх партиций в порядке публикации. Kafka хранит три копии каждой партиции. При `acks=all` продюсер получает подтверждение, когда запись приняли все синхронные реплики. Если один брокер отключится, две оставшиеся синхронные реплики смогут принимать записи, поскольку у топика задано `min.insync.replicas=2`. При временном сбое продюсер повторяет отправку и увеличивает паузу между попытками.

Вместе с событием продюсер передаёт ID схемы Avro. По этому ID ClickHouse находит схему в Karapace Schema Registry и разбирает сообщение. Таблица с движком Kafka читает события из топика, а материализованное представление записывает их в `cinema.events`. [Схема события](schemas/movie-event.avsc)

Таблица событий в ClickHouse разбита по месяцам. Внутри каждой партиции строки отсортированы по дате и UUID события. Когда сервис считает просмотры, он читает таблицу `ReplacingMergeTree` с `FINAL`, чтобы повторная доставка события не увеличила результат. Для удержания достаточно посчитать уникальных зрителей за день, поскольку несколько действий одного человека означают один возврат.

### Дневные метрики

DAU показывает, сколько разных пользователей совершили хотя бы одно действие за сутки по UTC. Место фильма в рейтинге зависит от числа начатых просмотров (`VIEW_STARTED`). Для конверсии число завершений (`VIEW_FINISHED`) делится на число стартов за те же сутки. Если стартов не было, конверсия не определена. Среднее время просмотра рассчитывается по `progress_seconds` только тех событий, в которых зритель досмотрел фильм.

Зрители, которые впервые включили фильм в один день, образуют когорту. ClickHouse хранит дату первого просмотра для каждого пользователя. Например, в понедельник в когорту вошли десять человек. Если в следующий понедельник трое из них снова смотрели кино, Grafana покажет 30 % в столбце «День 7». Для возврата нужно действие просмотра, поэтому поиск или лайк сами по себе его не дают. Если день уже наступил и никто не вернулся, в ячейке будет 0 %. Пока этот день впереди, ячейка остаётся пустой.

### Пересчёт и архив

Планировщик пересчитывает текущий день и предыдущие 14 дней, чтобы учесть опоздавшие события и возвраты зрителей. Пересчёт за более раннюю дату можно запустить по HTTP. Сервис заменяет дневную партицию в ClickHouse, а в PostgreSQL записывает метрики за день одной транзакцией. Если после обновления одной базы произойдёт сбой, планировщик найдёт незавершённый день и повторит расчёт.

После полуночи по UTC сервис ставит в очередь выгрузку за прошедший день. Если хранилище недоступно, задание остаётся в очереди до следующей попытки. После ручного пересчёта уже выгруженной даты сервис обновляет в SeaweedFS тот же файл `daily/YYYY-MM-DD/aggregates.json`, чтобы значения и время расчёта в S3 соответствовали данным PostgreSQL.

## Работа при отказе брокера

### Остановка одного брокера

```powershell
docker compose stop kafka1
```

При каждом запуске блока «Публикация события» создаётся новый `event_id`. Если строка с этим ID появляется в ClickHouse, пока `kafka1` выключен, значит, оставшиеся брокеры принимают записи.

### Восстановление брокера

```powershell
docker compose start kafka1
docker compose exec -T kafka2 /opt/kafka/bin/kafka-topics.sh --bootstrap-server kafka2:9092 --describe --topic movie-events
```

Когда брокер догоняет остальные, в поле `Isr` у каждой партиции снова появляются все три брокера. При остановке стенда командой `docker compose down` данные сохраняются в именованных томах.
